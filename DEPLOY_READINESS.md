## What is still needed before `deploy.sh sim` / `deploy.sh real` will run

All remaining gaps are on the **build toolchain**, not the models.

| Requirement | Current | Install |
|---|---|---|
| `just` (cmake wrapper used by `.justfile`) | not installed | `sudo apt install just` or `cargo install just` |
| `ninja` | not installed | `sudo apt install ninja-build` |
| `clang` | not installed | `sudo apt install clang` |
| `TensorRT_ROOT` env var | unset | Download TensorRT 10.x from NVIDIA Developer, extract to `~/TensorRT`, add `export TensorRT_ROOT=$HOME/TensorRT` and safe library path exports to a private shell rc or `gear_sonic_deploy/local_env.sh` |
| CUDA toolkit (nvcc) | available at `/usr/local/cuda/bin/nvcc` | Ensure this CUDA version matches the selected TensorRT package |
| C++ build | not built | From `gear_sonic_deploy/`: `source ../gear_sonic_deploy/local_env.sh`, `source scripts/setup_env.sh`, then `just build` |
| `onnxruntime` C API / CMake package | not visible (`onnxruntime_ROOT` unset) | Install ORT C/C++ package and set `onnxruntime_ROOT` to an install root containing `include/` and `lib/` if CMake cannot find it |

Until TensorRT, `just`, `ninja`, `clang`, and the ONNX Runtime C/C++ package are present, the C++ configure/build path is expected to fail before `deploy.sh sim` can launch.

## Launch invocation (once toolchain is ready)

Inspected from `gear_sonic_deploy/deploy.sh`; it will expand to:

```bash
cd gear_sonic_deploy
export TensorRT_ROOT=$HOME/TensorRT
./deploy.sh sim                 # loopback interface, --disable-crc-check set automatically
# or
./deploy.sh real                # auto-detects 192.168.123.x Unitree network
# or with explicit checkpoint:
./deploy.sh \
    --cp policy/release/model \
    --obs-config policy/release/observation_config.yaml \
    --planner planner/target_vel/V2/planner_sonic.onnx \
    --motion-data reference/example/walking_quip_360_R_002__A428 \
    --input-type manager \
    --output-type all \
    sim
```

Which ultimately runs (from the script):

```bash
just run g1_deploy_onnx_ref <iface> \
    policy/release/model_decoder.onnx \
    reference/example/ \
    --obs-config policy/release/observation_config.yaml \
    --encoder-file policy/release/model_encoder.onnx \
    --planner-file planner/target_vel/V2/planner_sonic.onnx \
    --input-type manager --output-type all --zmq-host localhost \
    [--disable-crc-check]   # sim only
```

## Sim preview of the released policy (without C++ deploy)

Until the C++ stack is built, you can sanity-check policies inside MuJoCo on the
already-working `.venv_sim`:

```bash
source .venv_sim/bin/activate
python decoupled_wbc/sim2mujoco/scripts/run_mujoco_gear_wbc_record.py \
    --config g1_gear_wbc_headless.yaml --cmd walk \
    --out rollouts/wbc_walk.mp4
```

This uses the `decoupled_wbc` ONNX policies (`GR00T-WholeBodyControl-Balance.onnx`,
`GR00T-WholeBodyControl-Walk.onnx`) — already LFS-pulled — and the
`g1_gear_wbc.xml` MJCF scene, with offscreen rendering to MP4.

Confirmed on this machine:

- `rollouts/wbc_balance.mp4` — robot holds pose at z≈0.75 m, xy drift < 10 cm over 8 s.
- `rollouts/wbc_walk.mp4` — robot walks forward ~3.5 m in 8 s on a 0.5 m/s command.

The SONIC ONNXs under `gear_sonic_deploy/policy/release/` use a different obs
schema (1762-dim encoder input with token_state + history observations — see
`observation_config.yaml`), so they are **not** drop-in for the simpler sim2mujoco
harness. They need the C++ deploy stack (which knows how to assemble those obs
buffers) or a matching Python harness wired through `gear_sonic/utils/mujoco_sim`.
